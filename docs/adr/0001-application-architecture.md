# ADR-0001：采用 TypeScript 模块化单体与独立 AI Worker

## 状态

Proposed

## 背景

产品由小团队从零开发，领域复杂但初期流量未知。同步业务包含项目、内容版本、权限、积分与导出；AI 阶段耗时较长且需要独立并发、重试和成本控制。当前没有证据支持微服务和 Kubernetes 的运维成本。

## 决策

- 使用 pnpm workspace 管理 TypeScript monorepo。
- Next.js 提供桌面工作台和移动审核 PWA。
- NestJS 模块化 API 承载同步业务。
- AI Worker 作为独立进程/部署单元，共享领域包和契约，但不与 API 同进程运行。
- PostgreSQL 为权威状态源；Redis/BullMQ 只承担异步运输与短期协调。
- API 使用事务 Outbox 发布任务，避免数据库成功但队列丢失。
- 使用 REST 处理命令和查询，SSE 推送任务进度。

## 后果

### 正面

- 单仓、单语言和共享契约适合小团队快速迭代。
- 模块边界先于网络边界，未来可以按证据拆服务。
- API 与 Worker 可以独立扩缩容并隔离长任务故障。
- PostgreSQL 事务覆盖版本、确认、积分和 Outbox。

### 负面

- 单一 API 部署的模块需要纪律防止耦合。
- Node Worker 处理 CPU 密集型解析时需要子进程或专用任务；不得阻塞事件循环。
- Redis/BullMQ 需要额外运维和任务恢复机制。

### 中性

- 微服务不是禁止，而是推迟到出现团队、负载或隔离证据之后。

## 备选方案

- **全 Serverless**：异步任务时长、供应商回调和大陆服务生态带来更强平台锁定，暂不采用。
- **微服务**：当前团队和规模不足以抵消分布式事务、部署和观测成本。
- **Python 全栈**：AI 生态强，但本产品主要复杂度是协作型 SaaS 和内容状态；保留未来 Python 专用 Worker 的接口，不作为首版主栈。
- **WebSocket**：当前只需服务器向客户端推送任务进度，SSE 更简单。

## 复核触发条件

- 单模块需要独立发布或不同技术栈。
- API 与 Worker 之外出现明确独立扩展瓶颈。
- 开发团队超过约 10 人且模块所有权稳定。
- 队列吞吐或可靠性超出 BullMQ/Redis 的运行边界。
