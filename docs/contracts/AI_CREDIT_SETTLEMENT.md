# AI 积分账本与任务结算契约（领域基础部分实现）

日期：2026-10-07。范围经用户确认：账本结构、结算状态机和验收用例；不写扣费代码，不接支付、套餐定价或生产计费。

依据：`SYSTEM_DESIGN.md` 的整数积分、流水余额、唯一业务键及任务/冻结/Outbox事务边界；T09 的成功项结算、失败项释放、BYOK不扣平台模型积分；`MODEL_TASK_RECOVERY.md` 的未知执行不重发规则。

后续用户确认了独立领域基础实施。`packages/billing` 现提供可信服务器账本服务及内存CAS仓储，选择固定事件ID＋规范化内容指纹协议，实现授予、冻结、结算/释放、未知/超报价待对账和BYOK exempt；不接现有任务或生产扣费。下述结构仍含未实现的持久化、Outbox、真实证据及费用资料，不能把整个契约视为已交付。包README说明具体范围。

## 1. 已定规则与实施前置条件

- 平台模型提交时冻结预计积分；可确认成功的计费单元结算，明确失败的单元释放冻结。
- BYOK仍要求有效高级订阅，但不冻结、不扣除对应平台模型积分。订阅费用与模型积分分开。
- 未知执行保留相关冻结并进入对账，不因为超时、无候选、断网、租约过期或页面关闭而退款或自动重发。
- 重复提交、回调、终态恢复和对账不得重复冻结、结算或释放；不能以更新任务状态代替账本流水。
- 用户积分与供应商成本分别记录。供应商收费不直接证明用户应扣积分；非法响应即使产生供应商成本，也不能自动视为可用成功内容。

当前任务运行链路仍仅有BYOK、任务幂等及候选恢复，没有平台凭据路线、持久化账本、生产积分授权或真实结算证据。独立账本不改变该运行链路；候选保存与任务终态尚非同事务，也未解除T09原有依赖。

## 2. 名词与计费责任

| 名词 | 定义 |
| --- | --- |
| 积分账户 | 工作室持有的平台模型积分权益账户，不是个人账户或人民币钱包 |
| 积分流水 | 不可变的权益变动记录；更正追加补偿记录，不覆盖历史 |
| 冻结 | 从可用额度转入任务预留，尚未消耗积分 |
| 结算 | 根据可信成功证据把冻结转为已消耗 |
| 释放 | 将尚未消耗的冻结恢复可用；界面可称退回，不代表现金退款 |
| 计费单元 | 在提交时固定、可独立验证和结算的任务范围，一般绑定scopeKey |
| 对账 | 根据持久化任务、结果和账本证据补齐状态，不能重新调用生成模型 |
| 计费责任 | 提交时固定的platform或byok，不能随当前Key/订阅变化改写 |

拆集建议当前为一个整体单元episode-plan，不能按模型临时输出的集数增加收费单元。故事知识当前初次提取的条目范围可能由模型返回，不能直接拿返回的scopeKey作为收费清单；需要先引入可信范围规划，或明确另行确认整任务计价。真实价格、单位映射及价格版本尚未定，实施不得自行采用其中一种。

## 3. 概念数据结构（非数据库迁移）

所有标识与业务唯一键包含workspaceId。积分使用非负整数最小单位并设明确数值上限；禁止浮点计算。数据库实现可用BIGINT，JSON接口需约定安全整数范围或十进制字符串，不能无损性未知地转换为JavaScript Number。

| 对象 | 最小资料与约束 |
| --- | --- |
| CreditAccount | workspaceId、unit、revision；余额是流水投影，可缓存但不能独立手改 |
| CreditGrant | grantId、来源类型、外部业务键、积分数量、授予时间；仅可信权益服务创建 |
| TaskBillingSnapshot | taskId、workspaceId、projectId、chapterId、责任、价格版本、quoteId、单元清单及每单元预留上限、总冻结量、创建时间；不可变，无Key/原文 |
| CreditEntry | entryId、workspaceId、taskId/unitId（按操作适用）、操作类型、数量、唯一业务键、证据引用、actor/service、requestId、创建时间 |
| UnitSettlement | taskId、unitId、状态、reserved/consumed/released、revision、证据版本；可变投影但事件不可变 |
| SettlementEvidence | 唯一证据ID、任务/单元、源版本和结果版本、结果判定、规则版本、来源、校验时间；只接受可信服务验证的资料 |
| ProviderCostRecord | 调用关联ID、计费责任、厂商/模型、usage、币种及整数成本（未知可为空）、成本状态和证据；与积分流水分离，不存Key或完整响应 |

单元清单只能由服务器确定，客户端不能提供可信积分数、责任、成功范围、账本操作或结算证据。供应商返回的数量、成本和scope必须与快照对齐；未知或重复单元不得进入扣费。

流水操作：grant、reserve、consume、release，必要更正为独立compensating entry。冻结业务键绑定taskId/unitId；结算/释放业务键绑定taskId/unitId/operation，部分变化采用固定事件ID或累计目标CAS，不能用每次随机requestId规避去重。相同业务键、不同内容拒绝，不能静默返回旧结果。

在不涉及有效期/撤销的首个基础模型中：

```text
预留余额 = Σreserve - Σconsume - Σrelease
可用余额 = Σgrant - Σconsume - 预留余额
单元 reserved = consumed + released + remainingReserved
```

三个余额都不得为负。重复冻结不增加余额占用；冻结不等于消耗。以上公式只覆盖grant/reserve/consume/release；补偿流水尚未定义代数方向，不得在实施时新增一个不计入余额投影的通用compensation操作。需先明确冲正关联、增减方向、权限及扩展不变量，再支持已消费积分的服务退款。以后若加入积分到期、订阅月度重置或授予撤销，必须显式记录相应权益事件及分配来源，不得把到期直接伪装为consume或覆盖账户余额。此类规则仍待产品确认。

## 4. 结算状态机（与生成状态分离）

平台计费单元：

```text
提交事务成功 → reserved
reserved → consumed             可信成功，所需积分等于预留
reserved → released             明确失败/确定未执行，释放全部
reserved → closed               成功消耗少于预留，同事务释放差额
reserved → reconciling          执行或证据未知，保持预留
reconciling → consumed/released/closed  补齐可信证据后幂等结算
```

BYOK为exempt：不创建reserve/consume/release，可记录责任、任务结果和供应商成本，不通过零金额扣费模拟收费。父任务汇总可为reserved、partially_settled、reconciling或settled；其中settled仅表示所有单元关闭，不表示全部成功。

| 生成情况 | 结算原则 |
| --- | --- |
| queued | 保留冻结，直到执行或确定终止 |
| succeeded | 仅对可信成功单元结算，校验任务指针、版本和范围；状态字样本身不够 |
| 部分成功 | 成功单元结算，明确失败单元释放，未知单元继续冻结 |
| 未发出调用前的明确拒绝 | 可依据可信调用边界证据释放；暂停状态本身不能证明未执行 |
| 模型已发出后超时/断网/恢复无候选 | reconciling，不释放、不自动重发 |
| 非法响应等明确业务失败 | 经可信失败证据确认后释放；供应商成本另记，不向用户暗扣 |
| 在途上游变化、权限撤销、候选无法写入 | 判定调用与交付是否明确；不能只按paused把冻结释放 |
| 用户点击取消或项目删除 | 不证明远端停止；未确定的单元保持对账，删除内容不删除账本 |

用户审核、拒绝候选或不继续下游不自动构成计费失败。计费成功以通过既定校验且可交付的结果为依据，而不是用户喜好；未来如提供服务退款，应走有权限和审计的补偿流程，不改原始成功证据。该质量边界应随具体阶段计价方案一并确认。

若可信结算额超过单元预留上限，不允许自动超扣或透支：进入reconciling，记录异常。定价实施必须确保可接受输出在预留范围内；加价、补充冻结或平台承担差额的产品策略尚待确认。

## 5. 事务、幂等与恢复边界

1. 提交：权限/订阅/原文与上游门禁、服务端报价后，在单个PostgreSQL事务内创建任务、固定计费快照、原子冻结并写Outbox。余额不足或任一步失败整体回滚，不允许无资金保障的platform任务成为可执行queued。
2. 并发冻结：锁定账户或受控CAS；不同任务争抢同一余额不能透支。重复请求先匹配持久化业务身份与指纹，不再次冻结。
3. 结算：可信结果校验后，把证据去重、单元状态CAS、consume/release流水及通知Outbox放入单个事务。若候选写入与其不在同一事务，必须有唯一任务/结果绑定和持久化对账扫描；不可宣称端到端恰好一次。
4. 回调：校验来源与任务绑定，保存净化证据；重复/乱序事件不能重新扣费或把已释放单元直接消费。终态相互冲突进入异常对账，不重写历史流水。
5. 恢复：读持久化候选、任务指针、证据与账本；不要依赖当前活动候选头，不调用生成模型。对账失败保留冻结并报警，不按等待时长猜测结果。
6. 重试：新任务只包含可重试失败范围，冻结新范围；旧任务已关闭的结算不重新记账。EXECUTION_UNCERTAIN在结果未澄清前禁止重提；更换Key不能改变旧任务责任。

现有任务requestId幂等只覆盖部分入口，初次故事知识提交尚未具备这套平台计费幂等边界。必须先补提交身份、事务仓储与Outbox再接平台扣费，不能只给现在的submit/run方法附加余额更新。

## 6. 权限与留存

工作室隔离；成员不能构造grant、冻结、结算、释放或重置流水。授予与补偿只允许可信后台服务，并记录操作者、原因和外部业务键。负责人可查看工作室余额和账单；其他成员账单可见范围、运营管理员裁决权限仍待确认，不从项目审核权限推导计费管理权。

对账证据只保留必要标识、校验结论及净化usage，不复制小说、提示词、Key或厂商私密错误。项目删除不能造成未结算任务失联；账本使用稳定工作室/任务ID与可删除内容解耦。计费数据留存、账号注销后的处理与内容删除策略的差异须另行明确，本文件不擅定永久保留或具体期限。
